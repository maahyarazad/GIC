# Research: Footer Newsletter Subscription and Admin-Added Subscribers

1. **Footer UI already exists.** `ui/src/Components/Footer/Footer.tsx` has the handler (regex validation, `POST /newsletter { email, active: true }`, toast) and the markup, but the markup is commented out. **Decision**: re-enable it and keep the validation message; surface server messages for 429 (limit) and 400 (already subscribed).
2. **Rate limiter key.** `express-rate-limit` keys on `req.ip`. `src/server.ts` does not set `trust proxy`, so behind nginx/pm2 every visitor shares the proxy's IP and one abuser would lock out everybody. **Decision**: add `app.set("trust proxy", 1)` (one proxy hop), confirm the deployment really sits behind exactly one proxy before shipping; otherwise `req.ip` is the proxy.
3. **Limit values.** Existing `strictLimiter` is 5 req/min (used for event attendance). **Decision**: a dedicated `subscribeLimiter`: 5 attempts per 10 minutes per IP, `standardHeaders: true`, JSON body `{ success:false, message:"Too many attempts. Please try again later." }`, status 429. A separate limiter keeps the budget independent of other endpoints.
4. **Admin routes are unauthenticated today.** `GET /newsletter`, `PUT /newsletter/{id}`, `DELETE /newsletter/{id}` have no middleware (the generated routes only call `fetchMiddlewares`, which are empty). **Decision**: add `@Middlewares(adminAuthMiddleware)` to those three. Admin-add uses `adminAuthMiddleware` too (roles `admin`, `procurement`, as for the newsletter articles). `GET/PUT email/{email}` (member profile toggle) are left untouched but flagged: they let anyone read or change any email's status. Follow-up: require a session and match the token's user email.
5. **Internal vs External.** **Decision**: derived in the list handler: collect the page's emails, `UserModel.find({ email: { $in: emails } }).select("email")`, mark `type: "internal"` when present else `"external"`. Emails are stored lowercase on both sides. Not stored, so it self-corrects when users register; not sortable/filterable (spec out-of-scope).
6. **Bulk add semantics.** **Decision**: `POST /api/v1/newsletter/admin/bulk` with `{ emails: string[] }` (UI splits on commas, whitespace, semicolons, new lines; max 200). For each unique, trimmed, lowercased valid email: not existing → insert active; existing inactive → set active; existing active → "duplicate". Returns `{ added, reactivated, duplicates, invalid: string[] }`. Uses `bulkWrite` upserts is avoided so counts are exact; a single `find({ email: { $in } })` then `insertMany`/`updateMany`.
7. **Modal.** **Decision**: use `ModalContext.openModal({ variant:"default", title, content, confirmText, disabled, onConfirm })` exactly like "Send Test Email" in `Newsletter.tsx` (content component writes to a ref; `setModalDisabled(!valid)`). A textarea for emails, live count of valid addresses.
8. **Enumeration note.** The public endpoint answers "already subscribed" for an active email (existing behaviour). Accepted, but rate limiting bounds probing. A generic response is a possible follow-up.
