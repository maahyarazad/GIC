# Implementation Plan: Email Log Service

**Branch**: `016-email-log-service` | **Date**: 2026-10-21 | **Spec**: [spec.md](spec.md)

**Input**: Feature specification from `specs/016-email-log-service/spec.md`

## Summary

Move the nodemailer transport into a new `src/services/emailLogService.ts` (the only file that imports nodemailer). Each send writes an `email_log` record that goes `pending` → `sent` / `failed`, without bodies or secrets and with a 365-day TTL. `sendRawEmailWithAttachments` delegates to it, so the 9 importers of `emailService.ts` don't change; they gain only an optional `kind` and a `runId` for bulk runs. An admin-only `GET /api/v1/email-logs` endpoint (in the style of the Contact Us list) feeds a new dashboard section, "Email Logs": a `GenericDataGrid` with column filters, a status select, a from/to date filter, and a View modal.

## Technical Context

**Language/Version**: TypeScript (Express + tsoa 6), React 19 (`ui/`)

**Primary Dependencies**: `nodemailer` 8 (existing), Mongoose 9 (existing), `adminOnlyMiddleware`, `GenericDataGrid`, `ModalContext.openModal`, `ToastContext`, `node:crypto.randomUUID`. No new packages.

**Storage**: MongoDB, a new collection `email_log` (see [data-model.md](data-model.md)) with a TTL index on `createdAt`

**Testing**: Manual, curl and mongosh per [quickstart.md](quickstart.md) (the repo has no test runner)

**Target Platform**: Linux server behind a reverse proxy; browser

**Project Type**: Web application (`src/` + `ui/src/`)

**Performance Goals**: At most 50 ms added per send (SC-005). Only one awaited single-document insert sits on the send path; the final update isn't awaited.

**Constraints**: Callers' results and errors stay exactly the same (FR-005). Logging failures never block a send (FR-006). Bodies, variables, attachment content and credentials are never stored (FR-007). Admin only (FR-011).

**Scale/Scope**: 1 new service, 1 model, 1 controller (1 GET route), 1 dashboard section; small edits to `emailService.ts`, `newsletterArticle.controller.ts` (test-send kind) and `Dashboard.tsx`. Volume: about one record per email, dominated by newsletter runs (one per active subscriber).

## Implementation Notes

1. **Service** ([research #1, #3](research.md)): `sendLoggedEmail` inserts a pending record (awaited, errors caught), builds the transport and sends inside `try`, then updates the record without awaiting, and returns or re-throws the original result. Address fields are normalized to lower-cased arrays and the error message is trimmed to 500 chars.
2. **Kind and run id** ([research #2](research.md)): `emailOtp` → `"otp_verification"`; `sendDynamicEmailToUser` → `template.name`; `sendDynamicEmailDoc` → `doc`; `sendMassDynamicEmailDoc` → `doc.name ?? "newsletter"`; `sendMassEmail` makes one `randomUUID()` per call and takes an optional `kind` (default `"bulk"`). Callers outside `emailService.ts` don't change, except the newsletter test send, which passes `kind: "newsletter_test"`.
3. **Endpoint** ([contract](contracts/email-logs.md)): reuse the filter, sort and pagination code style of `contactus.controller.ts`. Map `recipient` to `$or` over `to`, `cc` and `bcc`. Validate `status`, `from` and `to`. Run `find` and `countDocuments` in parallel. Return `{ logs, total, page, limit }`. Then regenerate the tsoa routes and spec (`npm run tsoa:routes && npm run tsoa:spec`) and commit them, as earlier features did.
4. **UI**: copy the fetch, debounce and pagination wiring from `ContactUsRequests.tsx`. Keep the toolbar state (`status`, `fromDate`, `toDate`) in the component, send `from` and `to` as ISO strings computed from local dates, and reset to page 1 when any of them changes. The View modal lists every field; failed records show the error in a `pre-wrap` block.
5. **Order**: model → service and `emailService.ts` wiring (US1–US3 can then be checked with mongosh) → controller and tsoa regen → dashboard section (US4).
