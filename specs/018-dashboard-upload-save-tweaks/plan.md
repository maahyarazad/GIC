# Implementation Plan: Dashboard Upload & Save Improvements

**Branch**: `018-dashboard-upload-save-tweaks` | **Date**: 2026-10-23 | **Spec**: [spec.md](./spec.md)

**Input**: Feature specification from `/specs/018-dashboard-upload-save-tweaks/spec.md`

## Summary

Three independent dashboard changes:

1. **Presentations lock-down**: drop the `user` role from the `manage_presentations` entry in the dashboard access map. The existing tab resolver already sends disallowed `?tab=` values to the role's default tab. On the server, the upload route moves from `authMiddleware` (any signed-in user) to `adminAuthMiddleware` (admin and procurement).
2. **Newsletter Save / Save and Close**: the form header's single submit button becomes **Save**, which calls the existing `submitArticle(html, { stay: true })` path, and **Save and Close**, which calls the existing path that returns to the list. Failure handling changes so that the editor never closes on an error.
3. **File Management multi-upload**: the file input accepts `multiple`. The client uploads the selected files **one request per file, sequentially**, to the existing `POST /api/v1/files`. It reports progress through axios `onUploadProgress`, the same mechanism `ui/src/api/presentations.ts` already uses, into a new blocking overlay with per-file and bytes-weighted batch progress. The `/files` write routes also get the admin/procurement guard that they are missing today.

## Technical Context

**Language/Version**: TypeScript. Server: Node with Express 4 and tsoa. UI: React 19 with Vite.

**Primary Dependencies**: tsoa (routes are generated from controllers), multer (memory storage, 50 MB limit set in `src/server.ts`), axios (`axiosInstance`), react-bootstrap, and the existing `useModal` / `useToast` providers.

**Storage**: MongoDB. Uploaded files are recorded in the `uploaded_files` collection, with the file bytes written to `file_storage/` and served at `/uploads`. Newsletter articles use the `newsletter-articles` collection. Neither schema changes.

**Testing**: The UI and server have no automated test framework. Validation is manual, following [quickstart.md](./quickstart.md).

**Target Platform**: Modern desktop browsers, with a Node server behind a reverse proxy.

**Project Type**: Web application. The server is in `src/` at the repo root and the SPA is in `ui/`.

**Performance Goals**: The progress display updates at least once per second during transfer (SC-005). A batch of 10 files finishes in one user action (SC-004).

**Constraints**: The 50 MB per-file multer limit stays. No new runtime dependencies. Upload progress comes from the HTTP upload stream, with no websocket or SSE channel (see [research.md](./research.md) R1).

**Scale/Scope**: Admin and procurement staff only, with batches of about 1–20 files. The work touches 1 server middleware decorator set, 2 controllers, and 4 UI components plus their CSS.
